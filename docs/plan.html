A system design for the next build Proposal · 28 Oct 2026

One host.
Every harness.

A terminal-first, programmable control surface for agents running on this machine or somewhere else. Keep the harnesses people already use. Give their sessions one coherent home.

The starting recommendationOne persistent TypeScript/Node host per machine and user, capability-aware harness drivers, durable session records, and the same small interface for the terminal, custom clients, and MCP orchestration. Measure before choosing a native host.
Implemented in this repository

Private local Git scaffold; Nix flakes; pnpm; TSRS; Oxlint; Oxfmt; a 1harness CLI with help and version output.

Proposed, not implemented

The host, harness drivers, persistent execution, remote connections, SDK, terminal agent view, extension worker, and orchestration MCP described below.

01 / Ownership before language

The host owns the work.
Clients come and go.

A laptop connection should never be the thing keeping a remote agent alive. Workspaces, provider credentials, native session handles, and running processes belong to the execution host.

Host-owned module

Session manager

Own the lifecycle once. Every client reaches the same command implementation.

Responsible for
Durable admission, session/run IDs, queue policy, driver ownership, recovery, and observable state.
Lifetime
Independent of any terminal connection. A session survives losing its observers.
Implementation
TypeScript first. One logical command writer per session; sessions run concurrently.

A session is a record and a queue. It does not automatically require another Node process.

A deep module

Small interface, substantial behavior

Callers learn sessions, submissions, observation, and explicit cancellation. Process ownership, retries, native protocol translation, and reconnect behavior live behind that interface.

Two separate MCP surfaces

Manage agents / provide tools

Orchestration MCP lets an agent start, inspect, message, wait on, and cancel 1harness sessions. Shared-tool MCP lets a managed harness call your custom tools. Both have explicit access and lifecycle owners.

02 / Make the guarantees explicit

“It kept running” has three meanings.

Continuing after a UI disconnect, recovering after a host crash, and resuming after a machine reboot are different capabilities. A durable database alone cannot restore an external harness process.

Accept, commit, dispatch, observe.

A client submits one command. Its acceptance and eventual completion are separate acknowledgements.

Illustrative walkthrough
01

Submit

Validate the request ID, target harness, workspace, and caller access.

02

Commit

Store the command and acknowledge durable admission after the transaction commits.

03

Dispatch

Invoke the driver. Record native session and run handles as they become known.

04

Observe

Store history and stream updates. Completion follows the actual harness lifecycle.

Invariant: an accepted submission is not a claim that execution has finished.
queued → running ↔ awaiting input → completed / failed / cancelledneeds reconciliation

These are proposed 1harness guarantees, not a simulator connected to real harnesses. The exact recovery contract must be verified for each driver.

The important crash window

“Recorded once” does not prove “executed once.”

A harness may perform an action before 1harness saves its acknowledgement. Retrying the same request ID can deduplicate 1harness admission; it cannot undo or automatically deduplicate an external side effect. Query native state and surface uncertainty before redispatching work.

03 / One contract, several implementations

Program the session.
Preserve the harness.

A client should work locally or remotely through the same 1harness contract. Drivers translate that contract into the native session protocol and report which operations are actually available.

Harness driver

Controls an existing agent

Codex, Claude Code, Pi, or FX. Preserves that harness’s prompts, tools, native history, and model behavior. This is the primary integration for 1harness.

Model provider

Makes direct inference requests

OpenAI, Anthropic, or another model endpoint. This belongs inside a harness or a deliberately added 1harness-native runtime. It is a separate interface.

PROPOSED SHAPE / not an implemented SDK 
const host = await connect({ host: "devbox" });

const session = await host.sessions.create({
  harness: "codex",
  workspace: "/srv/repos/project",
});

const run = session.submit(
  { text: "Investigate the failing tests" },
  { requestId: crypto.randomUUID(), whenBusy: "queue" },
);

await run.accepted; // stored before acknowledgement

for await (const event of session.observe({ after: savedCursor })) {
  render(event);
}

await session.cancel({ runId: run.id }); // explicit execution control
Stopping observation does not stop admitted work. Opening a host connection is separate from creating a session. Queue, steer, and reject-if-busy are explicit choices.

The examples communicate interface semantics. Names, signatures, and package layout are proposals; they are not a compatibility promise.

Driver surface Why it fits What to verify
Codex app-server[1] Structured threads, turns, events, and approval interactions. Pin tested versions. The official documentation labels app-server experimental. Reconcile turn state after interruptions.
Pi RPC[2] Long-lived subprocess with command acknowledgements and streamed events. Distinguish handling a prompt from settling work. Drain output continuously and handle extension interactions.
FX ACP[3] Structured integration intended for agent clients. Negotiate actual capabilities; ACP support alone does not establish native resume or steering parity.
Other harnesses Prefer supported structured protocols or SDKs. Use a driver worker when a JS SDK requires it. PTY-only integrations expose narrower terminal behavior. Declare those limits instead of inventing lifecycle events.
  • Stable identities: host, session, run, request, and event position have separate meanings.
  • Capability-aware behavior: native steering, resume, forking, and custom tool support are advertised explicitly.
  • Validation at the wire: one versioned schema defines the messages; TypeScript types alone do not validate remote input.
  • Preserve native details: a namespaced extension surface carries useful provider-specific metadata without changing the common lifecycle.
04 / The expensive part is often the architecture

Move less data.
Keep less in memory.

One shared host amortizes runtime overhead. A session should not create an extra JavaScript runtime merely to hold state. Harnesses can multiplex processes where their protocols support it.

total memory = host + extension workers + Σ harnesses & tools + bounded buffers

A native host primarily changes the host term. The size of that term relative to the complete workload has not been measured for 1harness.

Explore one design mistake / illustrative arithmetic

What happens if every update sends the whole transcript?

200 KiB

1 client
Full snapshot every update9.77 MiB/s
80-byte text deltas per update3.91 KiB/s

Payload only. No headers, compression, storage I/O, or runtime costs included. This is not a benchmark or a prediction of harness throughput.

Drain first

Continuously consume harness pipes. Undrained pipes can block the harness. A slow viewer must not block execution.[4]

Bound by bytes

Cap queues and message sizes. Store history on disk; page it on demand. Disconnect or resynchronize observers that fall too far behind.

Batch small changes

Coalesce display updates and text chunks. Commit admission and lifecycle state durably; specify the checkpoint and tail-loss contract for streaming text.

Persistence policy

Use the durability you actually promise.

SQLite WAL supports concurrent readers with one writer. FULL synchronization has stronger power-loss durability than NORMAL. Record critical state transactionally, acknowledge after the required commit, and keep synchronous database calls off the host’s control loop when needed. Streaming every token as a separate durable transaction is unnecessary work.[5]

05 / Three independent choices

Native is a tool.
Choose the job first.

The host language, extension runtime, and client SDK language can differ. A TypeScript client can control a Rust or Zig host. FX’s native engine and JavaScript library already demonstrate that separation.

TypeScript host · recommended starting point

What it buys

Direct integration with JS SDKs, ordinary TS/JS plugin loading, one shared runtime across sessions, and a straightforward development path.

What it costs

A JavaScript-engine baseline and garbage collection. CPU-heavy parsing or transforms can delay the event loop if they run directly on it.

Choose it when: integration flexibility and a coherent first implementation matter most. Profile parsing, fanout, and allocations before replacing the host.

Native already underneath

TypeScript coordinates native I/O.

Node’s event-driven sockets and pipes use native infrastructure. A worker per session is not an I/O optimization. Use a bounded worker pool for demonstrated CPU-heavy work, and a separate execution process when plugin fault containment is required.[6][7]

Concrete native candidates

Keep the seam narrow.

PTY integration, process-tree accounting, terminal rendering, indexing, or large diffs may justify native code or existing native bindings. Protocol policy, queue semantics, and tool registration can remain TypeScript.

PTY / process primitivesMeasured CPU bottleneckNative-backed renderer
ScriptC v0.4.5 / defer main runtime

A native compiler changes compatibility.

ScriptC compiles supported TS/JS into a native executable with its own runtime. The module graph is fixed at build time; runtime JS evaluation and Node native addons are unavailable. That conflicts with ordinary post-install TS/JS extensions and some PTY/database integrations. A small fixed helper remains a possible experiment; no ScriptC smoke test or performance measurement has been performed.[8]

Native code can improve the host’s baseline or a particular hot path. It does not automatically supply process-tree cancellation, reconnect semantics, or crash recovery. Installation can also package a JS runtime; your Nix setup can pin it alongside the application.

06 / Borrow the semantics; choose dependencies deliberately

What Pi and FX teach us.

Both projects run their own model/tool loops. 1harness coordinates those loops and other harnesses through drivers. An extensible agent runtime is useful inspiration, but it does not automatically become a universal harness controller.

PI / RELEASE 1.4.0

A layered TypeScript toolkit.

Pi separates model access, the agent loop, coding-agent behavior, and terminal rendering. Its SDK and RPC expose a programmable session; extensions customize behavior within Pi.

pi-ai → model connections
pi-agent-core → tool/model loop
pi-coding-agent → sessions & extensions
pi-tui → terminal rendering

Borrow: a small session interface and replaceable clients. Preserve driver capabilities when applying it to other harnesses.[9]

FX / RELEASE 0.0.15

A native engine with a JS interface.

FX’s CLI and agent engine are Zig. libfx exposes that engine through a Node addon and experimental WebAssembly, with host-provided tools.

Agent → configuration
Session → persistent conversation
Turn → work for one prompt
accepted ≠ completed

Borrow: durable admission, explicit turn results, request deduplication, and reconnectable observation.[10]

CHORD / PI 1.4.0

Typed objects across processes.

Chord offers runtime contracts, replicated state, links, and hot-reloadable code. It is a candidate for RPC or plugin plumbing, behind an internal seam.

Important limit: reference-owned remote objects can disappear after the last client disconnects. Reconnect snapshots are not durable event replay. The 1harness execution manager must own sessions independently.[11]

PI DURABLE / EXPERIMENTAL 1.4.0

Durability inside an agent runtime.

Commits before visibility, explicit task ownership, safe-replay tool contracts, and snapshot/watch behavior provide useful design lessons.

Important limit: those guarantees cover its own runtime. They do not restore arbitrary external harnesses or make their side effects replay-safe.[12]

07 / Frictionless is an ownership and connection feature

Make “somewhere else” feel local.

Start with your Mac controlling your Linux host. Execution stays on the host; connection discovery, installation, identity, and reconnection make the experience feel continuous.

Step Proposed behavior Why it matters
Connect once Resolve a named SSH host, identify its OS/architecture, negotiate versions, and start or reuse a compatible 1harness host. The user should not repeat setup for each session or harness.
Own the process Run the host independently of the SSH connection, using user-level system management: systemd on Linux, launchd on macOS. A dropped tunnel must not own execution lifetime. Exact shutdown and descendant-process policy needs testing.
Keep host identity Save the host’s identity and supported routes. Local sockets and authenticated remote routes expose the same contract. A route is a way to reach a machine, not the identity of that machine.
Reattach Load current session state, resume supported event observation, and fetch transcript pages only when needed. Returning to a session should not start a new run or resend its prompt.
Grow reach later Evaluate pairing and an optional encrypted relay after direct/SSH connections work. Off-network convenience is a separate delivery feature. A public relay is not required for the first personal-host build.
Execution locality

The workspace and credentials stay with the host.

The Mac supplies intent and renders results. The execution host resolves workspace paths, uses its installed harnesses, and owns their authentication. Tool calls and permissions must refer to that same environment.

Application ownership

One implementation of session commands.

The SDK, terminal, and orchestration MCP reach the same session manager. Authentication identifies callers; command handling checks what they may operate. No transport gets a separate lifecycle implementation.

08 / Sequence by evidence, not by package count

Build the smallest useful whole.

Each phase should demonstrate behavior through the public interface. These are proposed milestones, with no duration estimates or implied implementation progress.

00

Development foundation Scaffold exists

Local private repository, pinned pnpm/TSRS/Oxlint/Oxfmt, Nix development shell, and CLI entry point. No remote session engine has been implemented.

Already checked: type checking, lint, formatting, compilation, basic CLI behavior, and Nix evaluation. These checks do not validate the proposed architecture.
01

Two real harness drivers Proposed

Drive one real local session end to end, then a second harness—initial candidates Codex and Pi. Keep the common interface small and make capability differences visible.

Prove: submit, stream, handle interaction, detect real completion, and cancel. Two adapters establish which operations genuinely belong in the common contract.
02

A persistent host Proposed

Add durable admission, stable IDs, native handles, ordered commands, bounded streams, transcript storage, and reconciliation of interrupted dispatch.

Prove: a client can disappear without stopping work; duplicate submissions do not create a second run; uncertain outcomes remain explicit after restart.
03

The Mac → Linux vertical slice Proposed

Use one client contract through local and authenticated SSH/remote connections. Bootstrap a named host, negotiate versions, and reattach to existing sessions.

Prove: close the Mac terminal, reopen it, observe the same Linux-owned session, and control it without copying credentials or resending its prompt.
04

Programmability and orchestration Proposed

Expose the SDK, app-owned orchestration MCP, shared custom-tool MCP, and a loadable extension worker. Record delegated-task ownership and cancellation behavior.

Prove: one harness delegates work to another through 1harness; both remain visible; a shared custom tool works through two supported drivers.
05

The terminal experience and performance gate Proposed

Build the terminal agent view on the same client contract. Add reconnect/status UX, transcript navigation, and representative load measurements.

Prove: a separate custom client can reach equivalent session operations. Introduce native code only for a measured bottleneck or an explicit deployment constraint.
09 / “Efficient” needs a workload and a budget

Measure the host.
Test the promises.

There is no measured TypeScript-versus-native winner for 1harness yet. Use identical driver fixtures, payloads, persistence settings, and process lifetimes when comparing implementations.

Workload Measure Required outcome
Idle; 1, 10, 50 sessions Host-only memory and CPU; complete process-tree memory; marginal cost per session. Identify which term actually dominates. A session record should not imply a new runtime.
Normal streamed work Admission and delivery latency distributions; event-loop delay; database commit latency. Separate network, storage, driver, and UI costs before choosing an optimization.
One slow viewer Buffered bytes, disk growth, harness progress, healthy-viewer latency. Memory remains bounded; healthy clients and harness execution continue.
Disconnect and retry Request-ID behavior, observation cursor continuity, snapshot/transcript reconciliation. No duplicate admission; accepted work survives client loss.
Crash during dispatch Persisted command and native-session reconciliation. Do not blindly replay ambiguous external work. Show recoverable state or a concrete unresolved outcome.
Interrupt / terminate Provider-turn interruption and complete process-tree shutdown, separately. Stopping a turn and killing its processes remain distinct operations, verified on Linux and macOS.
When would a native host be justified?

When the host itself exceeds an agreed idle-memory, CPU, latency, or deployment budget after fixing avoidable processes, copies, and buffering. Compare a native implementation on the same workload; do not infer a multiplier from another project’s benchmarks.

Should Chord become the core framework?

Evaluate a small adapter first. Test object lifetime, reconnect behavior, plugin reload, and version compatibility against our session guarantees. Preserve 1harness-owned records and an explicit wire contract so framework lifetimes do not dictate execution lifetime.

What is still undecided?

Backend reuse versus an independent host, the exact protocol schema, streaming checkpoint policy, supported harness-version ranges, TUI library, extension-worker grouping, and distribution path beyond personal Nix hosts. Choose them through the first vertical slices rather than freezing a large speculative interface.

What does this plan intentionally leave for later?

A hosted relay, a direct-model agent runtime, broad provider parity, and a general native rewrite. They remain possible directions, with demonstrated need or evidence required before expanding the initial build.
